AI 世界观察与干预模拟器
产品与技术实施计划书 v0.1
一、项目概述
1.1 项目定位
本项目是一款以纯文字为主要表现形式的 AI 世界模拟游戏。
玩家不扮演世界中的任何角色，而是以世界创造者、观察者和有限干预者的身份：
创建或修改世界设定；
创建特殊角色；
从系统自动生成的人群中标记特殊角色；
观察特殊角色的第一视角想法、行动轨迹和对话；
安排未来发生的世界事件；
在角色主动寻求启示时给予建议；
离线后继续让世界运行；
接收角色发来的消息和重大事件通知。
特殊角色由独立 Agent 驱动。
每个 Agent 只能接触自己实际感知、听闻、记忆或推断出的信息，不共享全局上帝视角。玩家可以影响角色，
但不能直接控制角色，Agent 有权接受、部分接受、误解或拒绝玩家的建议。
1.2 核心体验
项目希望建立以下情感体验：
玩家创造一个世界，安排时代的风暴，选择值得关注的人，并观察他们如何在有限认知下活出自
己的人生。
玩家与角色之间不是操纵关系，而是一种逐渐变化的观察者关系：
角色可能相信玩家是神；
可能认为玩家是自己的直觉；
可能依赖启示；
可能质疑启示；
可能因错误建议而怨恨玩家；
也可能在长期沉默中学会独立。
1.3 产品核心原则
世界不会因为玩家离线而停止。
Agent 可以请求玩家帮助，但不能依赖玩家才能行动。
玩家提供的是建议，不是命令。

二、产品差异化
2.1 与传统 AI RPG 的区别
传统 AI RPG 通常以玩家扮演角色为中心：
玩家输入行动；
AI 生成剧情；
世界主要围绕玩家展开。
本项目中：
玩家不进入世界；
世界角色自主生活；
玩家观察而非扮演；
宏观事件不一定围绕特殊角色发生；
特殊角色可能错过事件、误解事件或死于事件；
玩家不能保证获得理想结果。
2.2 与普通多 Agent 小镇的区别
普通多 Agent 模拟往往强调：
日常生活；
NPC 对话；
工作、休息和社交；
简单关系形成。
本项目的重点是：
玩家自定义不同题材的世界；
角色严格局部认知；
世界事件驱动命运变化；
信息通过世界渠道传播；
特殊角色具备长期人格和记忆；
玩家能够通过启示与角色形成关系；
后台持续演化；
普通角色可以被升格为完整 Agent。

三、MVP 范围
3.1 MVP 验证目标
第一版不验证“能否模拟完整文明”，而验证以下四件事：
特殊角色是否表现出稳定而有差异的人格；
角色是否只使用自己实际知道的信息；
世界事件是否能够通过信息传播影响角色决策；
玩家是否会对无法完全控制的 Agent 产生持续关注。
3.2 MVP 世界规模
建议首个世界限制为：
1 个封闭城镇、空间站或殖民地；
5 至 8 个地点；
2 至 3 个主要组织；
30 至 50 个居民；
3 至 5 个特殊角色；
10 至 20 个中精度相关角色；
其余人物作为背景角色；
世界按小时推进；
一次模拟覆盖 7 至 30 个世界日。
3.3 MVP 场景建议
推荐使用“七日封锁城”作为首个演示世界：
第一天出现异常疾病；
第二天出现物资抢购；
第三天政府封锁城市；
第五天粮食运输停止；
第七天救援名额仅剩十个。
特殊角色可以包括：
医生；
政府基层官员；
小商人；
带孩子的单亲家长；
被怀疑传播疾病的外来者。

FastAPI 适合异步 API、流式响应和强类型数据模型；其官方文档提供异步处理与流式响应支持。
为什么选择 Python

后端职责
FastAPI 只负责：
用户请求；
数据查询；
创建工作流；
提交玩家回复；
向前端推送更新；
管理后台接口。
不应该使用普通 HTTP 请求进程执行长时间世界模拟。
FastAPI 自带的 BackgroundTasks 更适合请求结束后的轻量任务，长期世界运行应交给专门的持久化工作流系
统。
5.3 后台工作流与调度
正式方案：Temporal
推荐：
Temporal Server；
Temporal Python SDK；
独立 Worker 服务。
Temporal 的 Durable Execution 模型可以让工作流在进程崩溃、网络故障或服务重启后继续执行，并支持持续
数天、数月乃至更长时间的工作流。它非常适合角色等待玩家回复、定时世界事件和长期运行的 Agent 编排。

Temporal 负责的工作流
WorldWorkflow
每个世界一个长期工作流：
维护模拟运行状态；
推进世界时间；
获取下一个到期事件；
唤醒相关 Agent；
控制暂停和速度；
生成离线摘要。
AgentDecisionWorkflow
每次重大决策一个工作流：
生成决策上下文；
判断是否向玩家请求启示；
创建回应期限；
等待玩家 Signal；
收到回复后继续；
超时后独立决策；
写回结果。
ScheduledWorldEventWorkflow
负责玩家安排的世界事件：
等待目标世界时间；
检查触发条件；
发布客观状态变化；
启动信息传播；
唤醒相关角色。
原型期简化方案
如果团队规模较小，最初两周可以使用：
Celery；
Redis；
PostgreSQL 定时任务表。
但一旦启示等待窗口、长时间运行和故障恢复成为核心，就应迁移到 Temporal。不要自行实现一套复杂的定时
器和恢复系统。

MVP 数据量有限，PostgreSQL + pgvector 足够：
事务更简单；
世界状态和记忆在一个数据库；
易于备份；
运维成本较低；
可结合角色 ID、时间、地点和重要性做结构化过滤。

十八、首版成功标准
MVP 不以用户数量作为唯一标准。
建议重点观察：
玩家是否持续追踪同一个角色；
玩家是否会主动阅读离线摘要；
玩家是否因角色拒绝建议而产生情绪；
玩家是否会讨论“为什么这个角色这样做”；
玩家是否愿意创建第二个世界；
角色人格是否能维持至少数十次决策；
知识泄漏率是否足够低；
单世界运行成本是否可控；
玩家是否认为事件造成了长期影响；
玩家是否会把某个普通角色升格为特殊角色。
十九、推荐的首个技术里程碑
首个可运行版本只实现以下流程：
创建固定世界
↓
创建三个特殊 Agent
↓
推进世界时间
↓
发布“城市即将封锁”的秘密事实
↓
让信息通过不同渠道传播
↓
三个角色在不同时间获得不同版本
↓
其中一个角色请求玩家启示
↓
玩家回复或超时
↓
Agent 独立作出决定
↓
世界裁定行动结果
↓
玩家查看三人的想法、轨迹和对话
如果这个流程足够有吸引力，再继续做自由创世。
不要先建设庞大的通用世界编辑器，然后才验证角色是否值得关注。

二十一、项目最重要的技术原则
Agent 只能看到 Observation，不能看到世界。
Agent 只能提出 Action，不能直接修改世界。
世界事件先改变客观状态，再通过传播影响角色。
玩家启示是一条信息，不是一条系统命令。
后台世界以事件推进，不以固定频率调用所有 Agent。
记忆保存在外部系统中，当前 Prompt 只加载与当前决定有关的部分。
特殊角色的价值不在于生成更多文字，而在于持续拥有自己的认知、人格、目标和选择权。
